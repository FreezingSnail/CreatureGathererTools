## Non-Interactive Shell Commands

**ALWAYS use non-interactive flags** with file operations to avoid hanging on confirmation prompts.

Shell commands like `cp`, `mv`, and `rm` may be aliased to include `-i` (interactive) mode on some systems, causing the agent to hang indefinitely waiting for y/n input.

**Use these forms instead:**
```bash
# Force overwrite without prompting
cp -f source dest           # NOT: cp source dest
mv -f source dest           # NOT: mv source dest
rm -f file                  # NOT: rm file

# For recursive operations
rm -rf directory            # NOT: rm -r directory
cp -rf source dest          # NOT: cp -r source dest
```

**Other commands that may prompt:**
- `scp` - use `-o BatchMode=yes` for non-interactive
- `ssh` - use `-o BatchMode=yes` to fail instead of prompting
- `apt-get` - use `-y` flag
- `brew` - use `HOMEBREW_NO_AUTO_UPDATE=1` env var

## Agent Context Profiles

The managed Beads block is task-tracking guidance, not permission to override repository, user, or orchestrator instructions.

- **Conservative (default)**: Use `bd` for task tracking. Do not run git commits, git pushes, or Dolt remote sync unless explicitly asked. At handoff, report changed files, validation, and suggested next commands.
- **Minimal**: Keep tool instruction files as pointers to `bd prime`; use the same conservative git policy unless active instructions say otherwise.
- **Team-maintainer**: Only when the repository explicitly opts in, agents may close beads, run quality gates, commit, and push as part of session close. A current "do not commit" or "do not push" instruction still wins.

## Session Completion

This protocol applies when ending a Beads implementation workflow. It is subordinate to explicit user, repository, or orchestrator instructions.

1. **File issues for remaining work** - Create beads for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **Handle git/sync by active profile**:
   ```bash
   # Conservative/minimal/default: report status and proposed commands; wait for approval.
   git status

   # Team-maintainer opt-in only, unless current instructions forbid it:
   git pull --rebase
   bd dolt push
   git push
   git status
   ```
5. **Hand off** - Summarize changes, validation, issue status, and any blocked sync/commit/push step

**Critical rules:**
- Explicit user or orchestrator instructions override this Beads block.
- Do not commit or push without clear authority from the active profile or the current user request.
- If a required sync or push is blocked, stop and report the exact command and error.

## Project Goals

CreatureGathererTools is the authoring toolchain for **CreatureGathererFX**, a
GBA creature-battler (pixel arthouse game). The repo exists to turn human-authored
game content into engine-ready artifacts:

- **Visual content authoring** — create and edit maps, creatures, and moves in a
  desktop UI instead of hand-editing JSON.
- **Deterministic compilation** — compile authored JSON into the formats the
  engine consumes: C headers and a **PokerVM** binary bytecode blob (run by a VM
  from SPI-flash; see `crates/core/docs/binary_format.md`).
- **In-game scripting** — a small script language (branches, counters, locations,
  commands) parsed and assembled to bytecode for quest/event logic.
- **Tiled interoperability** — import/export maps via Tiled-style JSON
  (`crates/core/src/tiled.rs`).
- **Parity with the reference Go implementation** — integration tests assert zero
  discrepancy against the Go toolchain; the port must stay behavior-identical.
- **Offline, single-machine workflow** — no network services; everything runs
  locally; game data lives in a sibling checkout (`CreatureGathererFX`), wired in
  via `src-tauri/creature-tools.json` config.

## Architecture

Four layers, dependency direction `ui → src-tauri → crates/core → crates/wfc`:

### 1. React frontend — `ui/`

React 18 + TypeScript + Vite + Tailwind v4 + shadcn/ui (Radix) primitives. Runs as
the Tauri webview.

- Tab shell (`App.tsx`): Map / Creature / Move / Layout / WFC views stay mounted; inactive tabs
  are hidden via CSS to preserve per-view state. First-run SetupDialog for config.
  Editors remount only on config reload through `bootKey`.
- `editor.tsx` — map canvas editor (tile painting, palette, layers) plus tile-stamp paste and WFC-piece capture.
- `components/CreatureEditor.tsx`, `components/MoveEditor.tsx` — stat/field editors.
- `components/WfcTab.tsx`, `components/RecipePanel.tsx` — WFC piece, socket, recipe, anchor, preview, rule, and stamp authoring; the ephemeral six-entry hunk history tray stays in component state.
- `scriptPane.tsx` — script source editing with parse feedback from the backend.
- Pure logic extracted for unit testing: `state.ts`, `geometry.ts`, `tileset.ts`, `wfc.ts`,
  `lib/validation.ts`.
- Talks to the backend exclusively via `@tauri-apps/api` `invoke()` — never
  touches the filesystem or game data directly.

### 2. Tauri 2 shell — `src-tauri/` (crate `cgfx-app`, lib `cgfx_app_lib`)

Thin IPC layer over the core library. Rules:

- Every `#[tauri::command]` returns a serializable value or `Result<_, String>` —
  **no panics across IPC, no `clap` in this layer**.
- Commands wrap `creaturevm` (cgfx-core): `load_config`/`save_config`,
  `load_map`/`save_map`, `compile_map`, `parse_script`, `read_file_bytes`,
  `capture_piece`, `wfc_generate`, `wfc_validate`, `tiled_import_path(path, current)`, etc.
- App-level state is just the `Config`; stores are constructed per operation.

### 3. Rust core — `crates/core/` (lib `creaturevm`, bin `cgfx-tools`)

CLI + reusable library. Pipeline stages (see `src/main.rs`):

1. **Parse** (`parser/`) — load project JSON (creatures, moves, map).
2. **Process** (`processor/`) — lex/parse/assemble the script language to an AST
   (`ast.rs`) then to bytecode; `blob.rs` packs the binary.
3. **Write** (`writer/`) — emit C headers (`c.rs`) and the binary artifact
   (`bin.rs`, 24-bit little-endian via `u24.rs`). Binary layout: text block
   (offset table + ASCII blob) + bytecode block, padded to 256-byte alignment.

Supporting modules: `builder.rs`, `store.rs`, `config.rs`, `tiled.rs`, `model.rs`
(domain types: `Creature`, `GameMap`, `Move`), and `wfcmap/`. `wfcmap` persists
`GameMap.wfc` project data, including serde-default count/exclude/border/band rules,
and `GameMap.stamps` tile blocks; it slices variable-size pieces, compiles sockets,
anchors and placement presets, then bakes generated hunks. See
`crates/core/docs/wfc.md` for the slot model and deterministic generation contract.

### 4. Domain-free solver — `crates/wfc/` (crate `cgfx-wfc`)

`cgfx-wfc` accepts opaque symbols, directional adjacency rules, weights, presets,
and a grid. It owns deterministic xoshiro256** RNG, restart, propagation-step,
and memory limits; it has no map, tile, JSON, or filesystem dependency. Core's
`wfcmap` adapter is its only project-facing layer.

## Build & Test

```bash
# Rust core + shell
cargo build                                   # workspace: crates/core + src-tauri
cargo test                                    # unit + integration tests
cargo run -p cgfx-core -- <input.json> <output_dir>   # CLI only, no UI

# React frontend (from ui/)
npm install
npm run dev                                   # vite dev server (UI only)
npm test                                      # vitest run
npm run build                                 # typecheck (tsc) + vite build

# Full desktop app
npm run tauri dev                             # requires Rust toolchain
```

Test notes:

- Frontend tests are **vitest + Testing Library**, co-located as `*.test.ts(x)`
  next to the source they cover (`App.test.tsx`, `geometry.test.ts`, …).
- Backend tests live in `crates/core/tests/`; integration tests assert parity with
  the Go reference implementation.
- Rate-limiting/asset paths in `creature-tools.json` are machine-specific — do not
  commit changes to it.

## Conventions & Patterns

- **Rust**: edition 2024, `anyhow` for error context, `serde` derive for models,
  errors cross IPC only as strings. Mixed-case module names (e.g. `tiled.rs`) are
  intentional.
- **TypeScript**: strict; UI components never do I/O directly — go through
  `invoke`. Keep geometry/canvas math in pure modules so it can be unit-tested
  without a DOM.
- **Tests are permanent** — write them co-located with source, never in temp
  directories, never delete after running.
- **Git policy (default)**: conservative — no commits, pushes, or `bd dolt push`
  unless explicitly asked. Report changed files and propose next commands at
  handoff.
